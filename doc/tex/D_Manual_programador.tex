\section{Introducción}

Este apéndice recoge la información técnica necesaria para comprender, instalar, ejecutar, probar y mantener el proyecto desde el punto de vista de un programador. A diferencia de la documentación de usuario, centrada en el uso funcional de la aplicación, aquí se describen la estructura interna del sistema, los módulos principales y las formas de preparar un entorno de ejecución o desarrollo.

La aplicación se ha desarrollado en Python utilizando Flask como framework web. La persistencia se realiza mediante SQLAlchemy y Flask-SQLAlchemy sobre MariaDB. El procesamiento de imágenes se apoya en OpenCV, MediaPipe y Ultralytics/YOLO.

El proyecto puede ejecutarse de dos formas:

\begin{itemize}
	\item \textbf{Docker Compose}: opción recomendada para levantar el sistema completo de forma reproducible, incluyendo aplicación web y base de datos.
	\item \textbf{Entorno virtual de Python}: opción orientada al desarrollo local, depuración y ejecución directa de pruebas.
\end{itemize}

Desde el punto de vista del usuario final no es necesario conocer estos pasos técnicos. Una vez desplegado el sistema, el usuario accede simplemente desde un navegador web a la URL de la aplicación.

\section{Manual del programador}

Esta sección describe el funcionamiento interno de la aplicación desde el punto de vista de un desarrollador que necesite mantener o ampliar el sistema.

La arquitectura se basa en Flask, SQLAlchemy y una capa propia de servicios. Las plantillas HTML forman la interfaz, los controladores gestionan las peticiones HTTP, los modelos representan la persistencia y los servicios concentran la lógica de ejecución. La escalabilidad del proyecto se apoya especialmente en tres elementos: la base de datos, el orquestador de pipelines y la factoría de modelos de inteligencia artificial.

\subsection{Flujo interno de ejecución}

El flujo principal comienza cuando un usuario selecciona un pipeline, adjunta una imagen y solicita el análisis. El controlador recibe la petición, valida los datos, comprueba permisos y delega la ejecución en \texttt{PipelineRunner}.

El controlador principal se encuentra en:

\begin{bloqueCodigo}[title={Controlador principal}]
	app/controllers/pipeline_controller.py
\end{bloqueCodigo}

La ruta principal de análisis es:

\begin{bloqueCodigo}[title={Endpoint principal de análisis}]
	/api/v1/analizar
\end{bloqueCodigo}

El proceso seguido por esta ruta puede resumirse así:

\begin{enumerate}
	\item Recibe el identificador del pipeline, la imagen y la configuración opcional.
	\item Valida el archivo recibido y el JSON de configuración.
	\item Comprueba que el usuario tiene acceso al pipeline.
	\item Crea un registro en \texttt{EJECUCION}.
	\item Guarda la imagen original en \texttt{execution\_data/}.
	\item Ejecuta el pipeline mediante \texttt{PipelineRunner}.
	\item Registra los archivos generados en \texttt{TEMPORAL\_ARCHIVO}.
	\item Devuelve tokens de descarga, evitando exponer rutas internas del servidor.
\end{enumerate}

El orquestador se encuentra en:

\begin{bloqueCodigo}[title={Orquestador de pipelines}]
	app/services/pipeline_runner.py
\end{bloqueCodigo}

Su método principal es:

\begin{bloqueCodigo}[title={Método principal del orquestador}]
	PipelineRunner.ejecutar_pipeline(
			id_pipeline,
			imagen_inicial,
			config_completa=None,
			prefijo=""
	) -> tuple[list[str], list[dict]]:
	
\end{bloqueCodigo}

Este método consulta las etapas del pipeline, las ordena por el campo \texttt{orden}, obtiene el modelo y modo de cada etapa, resuelve el lanzador correspondiente mediante \texttt{AIFactory} y ejecuta cada modo sobre la imagen o imágenes de entrada.

El resultado devuelto tiene la forma:

\begin{bloqueCodigo}[title={Salida del orquestador}]
	(rutas_finales, resultados)
\end{bloqueCodigo}

donde \texttt{rutas\_finales} contiene las imágenes generadas y \texttt{resultados} contiene los datos estructurados de cada etapa. El sistema también permite salidas múltiples, por ejemplo cuando una etapa genera varios recortes y una etapa posterior procesa cada uno de ellos.

\subsection{Factoría de modelos de inteligencia artificial}

La factoría se encuentra en:

\begin{bloqueCodigo}[title={Factoría de modelos de IA}]
	app/services/ai_factory/__init__.py
\end{bloqueCodigo}

Su responsabilidad es devolver el lanzador adecuado según el nombre del modelo:

\begin{bloqueCodigo}[title={Resolución de lanzador}]
	AIFactory.get_launcher(nombre_modelo)
\end{bloqueCodigo}

Actualmente resuelve dos familias principales:

\begin{itemize}
	\item \texttt{yolo}: mediante \texttt{YoloLauncher}.
	\item \texttt{mediapipe}: mediante \texttt{MediaPipeLauncher}.
\end{itemize}

Todos los lanzadores cumplen la interfaz común definida en:

\begin{bloqueCodigo}[title={Interfaz común de lanzadores}]
	app/services/ai_factory/interface.py
\end{bloqueCodigo}

El método obligatorio es:

\begin{bloqueCodigo}[title={Contrato común de ejecución}]
	def ejecutar_modo(
			self,
			modo_nombre: str,
			imagen_path: str,
			config: Dict[str, Any] = None,
			prefijo: str = ""
	) -> Tuple[Union[str, List[str]], Dict[str, Any]]:
\end{bloqueCodigo}

Su salida esperada es:

\begin{bloqueCodigo}[title={Salida esperada de un launcher}]
	(rutas_generadas, datos_json)
\end{bloqueCodigo}

El primer elemento puede ser una ruta o una lista de rutas. El segundo debe ser un diccionario con los resultados estructurados del análisis.

\subsection{Configuración por etapas}

Cada modo puede tener una configuración predeterminada almacenada en formato JSON dentro del directorio \texttt{configs/}. La ruta de dicha configuración se guarda en:

\begin{bloqueCodigo}[title={Campo de configuración predeterminada}]
	IA_MODO.config_predeterminada
\end{bloqueCodigo}

Cuando el usuario solicita la configuración de un pipeline, el endpoint:

\begin{bloqueCodigo}[title={Endpoint de configuración de pipeline}]
	/api/v1/configuracion_pipeline/<id_pipeline>
\end{bloqueCodigo}

devuelve la configuración agrupada por etapas:

\begin{bloqueCodigo}[title={Formato de configuración por etapas}]
	{
		"etapa_1": { ... },
		"etapa_2": { ... }
	}
\end{bloqueCodigo}

Durante la ejecución, \texttt{PipelineRunner} obtiene la configuración concreta de cada etapa mediante:

\begin{bloqueCodigo}[title={Obtención de configuración por etapa}]
	config_completa.get(f"etapa_{etapa.orden}", {})
\end{bloqueCodigo}

Por tanto, si se añade un nuevo modo, sus parámetros deben estar definidos en un fichero JSON y ser interpretados por la función Python correspondiente.

\subsection{Relación con la base de datos}

La ampliación del sistema no depende solo del código. Para que un modelo, modo o pipeline pueda utilizarse desde la aplicación, también debe estar registrado en la base de datos.

Las entidades principales implicadas son:

\begin{itemize}
	\item \texttt{IA\_MODELO}: familias de modelos disponibles.
	\item \texttt{IA\_MODO}: modos asociados a cada modelo.
	\item \texttt{PIPELINE}: flujos de procesamiento.
	\item \texttt{PIPELINE\_ETAPA}: etapas concretas de cada pipeline.
\end{itemize}

La tabla \texttt{PIPELINE\_ETAPA} incluye \texttt{id\_ia} e \texttt{id\_modo}. La clave foránea compuesta con \texttt{IA\_MODO} evita que una etapa asocie un modo a un modelo al que no pertenece.

Para que una etapa sea válida deben coincidir el modelo, el modo, la relación \texttt{id\_ia}--\texttt{id\_modo}, el nombre esperado por el lanzador y el fichero de configuración asociado.

\subsubsection{Añadir un nuevo modo a un modelo existente}

Añadir un nuevo modo implica incorporar una operación nueva a una familia ya soportada, como YOLO o MediaPipe. No requiere modificar \texttt{AIFactory}; el cambio se concentra en el lanzador del modelo, la función de procesamiento, la configuración y la base de datos.

El procedimiento mínimo es:

\begin{enumerate}
	\item Crear un fichero JSON de configuración en \texttt{configs/}.
	\item Crear el archivo Python del nuevo modo dentro de la carpeta del modelo.
	\item Implementar una función con el contrato común:
\end{enumerate}

\begin{bloqueCodigo}[title={Contrato de un nuevo modo}]
	def ejecutar_modo(
			self,
			modo_nombre: str,
			imagen_path: str,
			config: Dict[str, Any] = None,
			prefijo: str = ""
	) -> Tuple[Union[str, List[str]], Dict[str, Any]]:
\end{bloqueCodigo}

A continuación se completa el registro del modo:

\begin{enumerate}
	\setcounter{enumi}{3}
	\item Registrar la función en el lanzador correspondiente.
	\item Añadir el modo en \texttt{IA\_MODO}.
	\item Añadirlo en \texttt{seed.py} si debe formar parte del entorno inicial.
	\item Crear o actualizar pipelines desde administración o desde \texttt{seed.py}.
	\item Añadir pruebas automatizadas.
\end{enumerate}

El nombre usado como clave en el lanzador debe coincidir con \texttt{IA\_MODO.nombre\_modo}. Se recomienda utilizar nombres en minúsculas, sin espacios y sin tildes.

\subsubsection{Añadir un nuevo modelo de inteligencia artificial}

Añadir una nueva familia de modelos requiere crear una nueva carpeta dentro de la factoría, implementar un lanzador propio, registrarlo en \texttt{AIFactory} y añadir el modelo y sus modos a la base de datos.

El procedimiento mínimo es:

\begin{enumerate}
	\item Revisar dependencias Python y librerías del sistema.
	\item Actualizar \texttt{requirements.txt}, \texttt{requirements.lock} y, si procede, \texttt{Dockerfile}.
	\item Crear una carpeta en \texttt{app/services/ai\_factory/}.
	\item Implementar un \texttt{launcher.py} que herede de \texttt{IALauncherBase}.
	\item Implementar los modos de procesamiento.
	\item Registrar el nuevo lanzador en \texttt{AIFactory}.
	\item Crear los ficheros JSON de configuración.
	\item Añadir el modelo en \texttt{IA\_MODELO}.
	\item Añadir sus modos en \texttt{IA\_MODO}.
	\item Crear pipelines asociados desde administración o desde \texttt{seed.py}.
	\item Añadir pruebas de factoría, lanzador, modo y pipeline.
\end{enumerate}

En condiciones normales no debería ser necesario modificar nada en \texttt{pipeline\_controller.py}, \texttt{PipelineRunner} ni las tablas principales del modelo relacional. La ampliación debe concentrarse en los nuevos módulos de procesamiento, el lanzador, la factoría, la configuración, los registros de base de datos y las pruebas.

\subsection{Gestión de archivos generados}

Los modos de procesamiento guardan sus salidas como archivos físicos. El usuario no recibe rutas internas, sino tokens asociados a registros en \texttt{TEMPORAL\_ARCHIVO}.

Las funciones de procesamiento deben guardar los resultados en el directorio de trabajo recibido en \texttt{imagen\_path}. El nombre del archivo debe incorporar el \texttt{prefijo} cuando sea necesario mantener trazabilidad entre etapas.

Ejemplos de nombres utilizados en el proyecto son:

\begin{itemize}
	\item \texttt{deteccion\_<nombre\_archivo>} para detecciones YOLO.
	\item \texttt{recorte\_<indice>\_<nombre\_archivo>} para recortes de personas.
	\item \texttt{mp\_<nombre\_archivo>} para detección de manos.
	\item \texttt{mp\_pose\_<nombre\_archivo>} para estimación de pose.
\end{itemize}

Cuando se utilice OpenCV, debe comprobarse explícitamente el resultado de \texttt{cv2.imwrite()}, ya que puede devolver \texttt{False} si no consigue guardar el archivo.

\subsection{Ejecución mediante Docker Compose}

La ejecución mediante Docker Compose es la opción recomendada para probar el sistema completo de forma reproducible, ya que levanta conjuntamente la aplicación web y la base de datos.

Esta forma de ejecución es válida tanto en sistemas Linux como en Windows, siempre que Docker y Docker Compose estén disponibles. En Windows se recomienda utilizar Docker Desktop y ejecutar los comandos desde PowerShell, Git Bash o una terminal equivalente. No es necesario instalar Python, MariaDB ni las dependencias internas del proyecto en el equipo anfitrión, ya que estos componentes se ejecutan dentro de contenedores.

\subsubsection{Configuración del archivo .env}

Si existe \texttt{.env.example}, se copia para crear el fichero de configuración local. En Linux, Git Bash o PowerShell puede utilizarse:

\begin{bloqueTerminal}[title={Creación del fichero de entorno}]
	cp .env.example .env
\end{bloqueTerminal}

En caso de utilizar la terminal clásica de Windows, el comando equivalente sería:

\begin{bloqueTerminal}[title={Creación del fichero de entorno en cmd}]
	copy .env.example .env
\end{bloqueTerminal}
Una configuración de ejemplo para Docker Compose es:

\begin{bloqueCodigo}[title={Ejemplo de configuración .env para Docker Compose}]
	SECRET_KEY=CAMBIAR_CLAVE_FLASK
	JWT_SECRET_KEY=CAMBIAR_CLAVE_JWT
	
	MARIADB_ROOT_PASSWORD=CAMBIAR_PASSWORD_ROOT
	MARIADB_DATABASE=ia_orquestada_db
	MARIADB_USER=usuarioIAOrquestadaDB
	MARIADB_PASSWORD=CAMBIAR_PASSWORD_USUARIO
	
	DATABASE_URL=mysql+pymysql://usuarioIAOrquestadaDB:CAMBIAR_PASSWORD_USUARIO@db:3306/ia_orquestada_db?charset=utf8mb4
\end{bloqueCodigo}

Los valores anteriores son de ejemplo. En un entorno real deben sustituirse por claves y contraseñas propias. Dentro de Docker, el host de la base de datos es \texttt{db}, no \texttt{localhost}.

\subsubsection{Arranque inicial}

Antes de arrancar los servicios puede validarse la configuración:

\begin{bloqueTerminal}[title={Validación de Docker Compose}]
	docker compose config
\end{bloqueTerminal}

El primer arranque puede realizarse en tres pasos:

\begin{bloqueTerminal}[title={Primer arranque del sistema}]
	# 1. Construir y arrancar la base de datos
	docker compose up -d --build db
	
	# 2. Inicializar esquema y datos de demostración
	docker compose run --rm web python seed.py
	
	# 3. Arrancar la aplicación web
	docker compose up -d web
\end{bloqueTerminal}

\subsubsection{Acceso desde el equipo y otros equipos de la red local}

Por defecto, cuando la aplicación se ejecuta en Docker y el puerto está publicado correctamente, puede accederse desde el propio equipo anfitrión mediante:

\begin{bloqueCodigo}[title={Acceso desde el equipo anfitrión}]
	http://localhost:5000
\end{bloqueCodigo}

Sin embargo, si se desea acceder desde otro equipo conectado a la misma red local, no debe utilizarse \texttt{localhost}, ya que ese nombre siempre hace referencia al propio equipo desde el que se abre el navegador. En su lugar, debe utilizarse la dirección IP del equipo donde se está ejecutando Docker.

Para que el acceso desde otros equipos funcione, deben cumplirse tres condiciones:

\begin{itemize}
	\item La aplicación debe escuchar en \texttt{0.0.0.0:5000}, permitiendo conexiones externas al contenedor.
	\item El servicio web debe publicar el puerto mediante Docker Compose.
	\item El firewall del equipo anfitrión debe permitir conexiones entrantes al puerto \texttt{5000}.
\end{itemize}

En el fichero \texttt{docker-compose.yml}, el servicio web debe incluir una asignación de puertos como la siguiente:

\begin{bloqueCodigo}[title={Publicación del puerto en Docker Compose}]
	ports:
	- "5000:5000"
\end{bloqueCodigo}

Esta configuración indica que el puerto \texttt{5000} del equipo anfitrión se redirige al puerto \texttt{5000} del contenedor. Si se utilizase una configuración limitada a \texttt{127.0.0.1}, el acceso quedaría restringido al propio equipo.

Para conocer la dirección IP del equipo anfitrión en Linux puede ejecutarse:

\begin{bloqueTerminal}[title={Consulta de IP en Linux}]
	hostname -I
\end{bloqueTerminal}

También puede consultarse con:

\begin{bloqueTerminal}[title={Consulta detallada de interfaces en Linux}]
	ip addr
\end{bloqueTerminal}

En Windows, la dirección IP puede obtenerse desde PowerShell o símbolo del sistema mediante:

\begin{bloqueTerminal}[title={Consulta de IP en Windows}]
	ipconfig
\end{bloqueTerminal}

Una vez conocida la dirección IP del equipo donde se ejecuta Docker, desde otro equipo de la misma red se accede sustituyendo \texttt{localhost} por dicha dirección. Por ejemplo:

\begin{bloqueCodigo}[title={Acceso desde otro equipo de la red local}]
	http://192.168.1.27:5000
\end{bloqueCodigo}

Si el sistema operativo bloquea las conexiones entrantes, será necesario permitir el puerto \texttt{5000} en el firewall. En sistemas Linux con \texttt{ufw}, puede hacerse con:

\begin{bloqueTerminal}[title={Apertura del puerto 5000 en Linux}]
	sudo ufw allow 5000/tcp
\end{bloqueTerminal}

En Windows, debe permitirse el acceso a Docker Desktop o crear una regla de entrada para el puerto \texttt{5000} en el Firewall de Windows.

Esta configuración está pensada para pruebas dentro de una red local. Para exponer la aplicación a Internet sería necesario un despliegue más completo, con servidor público, configuración de red, dominio, HTTPS y, preferiblemente, un proxy inverso. Por ese motivo, en este proyecto el acceso externo se contempla únicamente para entornos de demostración o pruebas dentro de la misma red.

Se accede a MariaDB:

\begin{bloqueTerminal}[title={Acceso a MariaDB}]

Se crea la base de datos y el usuario:

	GRANT ALL PRIVILEGES ON ia_orquestada_db.*
	TO 'usuarioIAOrquestadaDB'@'localhost';
	
	FLUSH PRIVILEGES;
	EXIT;

\subsection{Gestión del fichero requirements.lock}

El fichero \texttt{requirements.lock} se utiliza para construir la imagen Docker de forma más controlada, fijando versiones y hashes. No debe editarse manualmente.

Cuando se modifique \texttt{requirements.txt}, se regenera con:

\begin{bloqueTerminal}[title={Regeneración de requirements.lock}]
	python -m pip install pip-tools
	python -m piptools compile --generate-hashes --output-file=requirements.lock requirements.txt
\end{bloqueTerminal}

Después se recomienda comprobar la construcción de la imagen:

\begin{bloqueTerminal}[title={Comprobación de construcción Docker}]
	docker compose build --no-cache web
\end{bloqueTerminal}

No se recomienda ejecutar \texttt{pip freeze > requirements.txt} tras instalar herramientas auxiliares, ya que podría añadir dependencias que no forman parte de la ejecución real de la aplicación.

\subsection{Integración continua y análisis estático con SonarCloud}

Además de las pruebas ejecutadas en local, el proyecto se ha integrado con GitHub Actions y SonarCloud. Esta integración permite ejecutar análisis automáticos orientados a detectar problemas de mantenibilidad, seguridad, duplicación, complejidad o prácticas no recomendadas.

El análisis se ejecuta automáticamente cuando se realizan cambios sobre las ramas principales del proyecto, concretamente en operaciones de \textit{push} o \textit{pull request} hacia \texttt{main} o \texttt{develop}. De esta forma, la calidad del código puede revisarse durante el desarrollo y antes de integrar cambios en ramas estables.

El flujo de integración continua prepara un entorno Linux, configura Python 3.11, instala las dependencias del sistema necesarias para las librerías de visión por computador, instala las dependencias Python del proyecto y ejecuta las pruebas con cobertura. Posteriormente, SonarCloud toma como entrada el informe de cobertura generado y realiza el análisis estático del código.

También se han definido exclusiones específicas para la cobertura. En este caso se excluyen las pruebas, el script de inicialización, el punto de entrada, la configuración y los archivos \texttt{\_\_init\_\_.py}. Estos elementos tienen poca lógica funcional propia o actúan como código de arranque, configuración o ensamblado. Por ello, incluirlos en la cobertura podría alterar la métrica sin aportar información útil sobre la validación de la lógica principal del sistema.

El código más relevante de la aplicación, como controladores, servicios, factoría de modelos, ejecución de pipelines, entidades persistentes de la aplicación y funciones de procesamiento, permanece dentro del análisis. Por tanto, la configuración busca que las métricas se centren en el código mantenido y ejecutable del proyecto, evitando ruido provocado por recursos externos o generados.

Durante la integración se revisaron incidencias señaladas por la herramienta y se aplicaron correcciones relacionadas con la construcción Docker, la gestión de dependencias y determinados patrones sensibles desde el punto de vista de seguridad. De esta forma, SonarCloud se ha utilizado como apoyo a la revisión técnica del proyecto.

La estrategia de validación combina tres niveles:

\begin{itemize}
	\item \textbf{\texttt{pytest}}: valida el comportamiento funcional del backend.
	\item \textbf{\texttt{pytest-cov}}: mide la cobertura de código ejercitada por las pruebas.
	\item \textbf{SonarCloud}: revisa calidad, seguridad y mantenibilidad mediante análisis estático.
\end{itemize}
