\apendice{Plan de Proyecto Software}

\section{Introducción}

Este apéndice recoge la planificación temporal y el estudio de viabilidad del proyecto. Aunque se ha tomado Scrum como referencia para organizar el trabajo de forma iterativa, su aplicación se ha adaptado a las características de un Trabajo Fin de Grado desarrollado por una sola persona. Por tanto, no se ha aplicado como una metodología ágil completa de equipo, sino como una forma de estructurar tareas, revisar avances y planificar incrementos sucesivos.

La planificación se ha dividido en sprints de corta duración, cada uno con un objetivo, un criterio de aceptación y un conjunto de tareas estimadas. Para el seguimiento del trabajo se han empleado puntos de historia, usando como equivalencia práctica que 8 puntos representan una jornada completa de trabajo. Esta estimación ha permitido comparar el esfuerzo previsto con el avance real y ajustar los siguientes sprints conforme evolucionaba el proyecto.

\section{Estudio de viabilidad}

El estudio de viabilidad analiza el proyecto desde dos perspectivas: la económica, centrada en estimar el coste aproximado de desarrollo y la posible recuperación de la inversión; y la legal, orientada a revisar las licencias de software, modelos utilizados, documentación y tratamiento de datos personales.

\subsection{Viabilidad económica}

Aunque el proyecto se ha desarrollado en el contexto de un Trabajo Fin de Grado, se ha estimado el coste que tendría realizar una aplicación de estas características en un entorno profesional. Para ello se han considerado costes de personal, hardware amortizado, software y gastos generales.

\paragraph{Costes de alojamiento en producción}

Además de los costes de desarrollo, se ha realizado una estimación orientativa del coste mensual que tendría alojar la aplicación en un entorno de producción básico. Para esta estimación se ha tomado como referencia una arquitectura sencilla en AWS, manteniendo la idea actual del proyecto basada en Docker y consultando los precios públicos de Amazon EC2, Amazon EBS, Amazon S3 y direcciones IPv4 públicas~\cite{aws_ec2_pricing,aws_ebs_pricing,aws_s3_pricing,aws_public_ipv4_pricing}.

La opción seleccionada sería desplegar la aplicación en una instancia EC2 con Docker Compose, ejecutando el contenedor de la aplicación Flask y el contenedor de MariaDB. Los archivos generados por las ejecuciones podrían almacenarse inicialmente en un volumen persistente EBS, aunque en un entorno de producción sería recomendable utilizar Amazon S3 para desacoplar los resultados temporales de la instancia principal.

Los servicios considerados son los siguientes:

\begin{itemize}
	\item \textbf{Amazon EC2}: servidor principal para ejecutar los contenedores Docker de la aplicación y la base de datos.
	\item \textbf{Amazon EBS}: volumen persistente para sistema, base de datos, modelos locales y ficheros necesarios por la aplicación.
	\item \textbf{Amazon S3}: almacenamiento de imágenes y resultados temporales generados por los usuarios.
	\item \textbf{IPv4 pública}: dirección necesaria para exponer la aplicación desde Internet.
\end{itemize}

Se ha descartado inicialmente el uso de una base de datos gestionada como Amazon RDS para mantener una estimación contenida y coherente con el despliegue actual mediante Docker. En una explotación más exigente, Amazon RDS para MariaDB sería una alternativa más robusta para gestionar copias de seguridad, disponibilidad y mantenimiento de la base de datos, aunque incrementaría el coste mensual~\cite{aws_rds_mariadb_pricing}.

\subsubsection{Protección de datos personales}

La aplicación trata datos personales como cuentas de usuario, correos electrónicos, contraseñas cifradas, servicios contratados y registros de ejecuciones. Por ello, se han tenido en cuenta los principios del Reglamento General de Protección de Datos y de la Ley Orgánica 3/2018, especialmente en relación con la minimización, confidencialidad y limitación de conservación de los datos~\cite{rgpd_2016_articulo_17,boe_lopdgdd_2018}.

Desde el diseño se han aplicado medidas como el almacenamiento de contraseñas mediante hash, la gestión temporal de imágenes y resultados, el acceso a archivos mediante tokens de descarga y la asociación de ejecuciones al usuario autenticado. En una explotación real sería necesario completar esta parte con una política de privacidad, condiciones de uso y procedimientos formales para el ejercicio de derechos.
