\capitulo{5}{Aspectos relevantes del desarrollo del proyecto}

En este capítulo se recogen los aspectos más importantes del desarrollo del proyecto, desde la validación técnica inicial hasta la consolidación de una plataforma \textit{web} modular y extensible. Se explican las decisiones que marcaron el diseño final, los problemas más relevantes encontrados durante el desarrollo y las soluciones aplicadas.

La aportación principal del proyecto no está únicamente en ejecutar modelos sobre imágenes, sino en haber construido una base capaz de organizar modelos, modos de ejecución, \textit{pipelines}, permisos, resultados temporales y tareas de administración de forma coherente. Para explicar esta evolución, el desarrollo se resume en tres fases:

\begin{itemize}
	\item \textbf{Validación técnica inicial.} Construcción de una demo para comprobar la ejecución de modelos de visión por computador desde una aplicación \textit{web}.
	\item \textbf{Diseño de la aplicación escalable.} Definición de la arquitectura modular, el modelo de datos, la factoría de modelos, los \textit{pipelines}, la configuración por etapas y la lógica de acceso.
	\item \textbf{Consolidación funcional.} Implementación de la administración de \textit{pipelines}, resultados temporales, pruebas automatizadas, análisis estático, datos iniciales y despliegue reproducible.
\end{itemize}

\section{Validación técnica inicial}

El primer objetivo fue comprobar si el flujo básico de procesamiento era viable dentro de una aplicación \textit{web}. Antes de diseñar usuarios, planes, permisos o administración, era necesario validar la parte de mayor riesgo técnico: recibir una imagen desde el navegador, procesarla en el servidor y devolver un resultado interpretable.

El flujo validado fue el siguiente:

\begin{enumerate}
	\item Subida de una imagen desde el navegador.
	\item Recepción y almacenamiento temporal en el servidor.
	\item Selección del modelo y modo de procesamiento.
	\item Ejecución del análisis en el \textit{backend}.
	\item Generación de una imagen procesada.
	\item Devolución de una salida visual y estructurada.
\end{enumerate}

La demo permitió comprobar dos tipos de análisis: detección de objetos mediante cajas delimitadoras y estimación de puntos clave mediante \textit{landmarks}. La Figura~\ref{fig:AppDemoMediapipe1} muestra una de las capturas de esta fase inicial, suficiente para representar el alcance de la demo: una imagen enviada desde la interfaz, procesada en el servidor y devuelta con anotaciones visuales.

\begin{figure}[htbp]
	\centering
	\includegraphics[width=0.40\textwidth]{AppDemoMediapipe1.png}
	\caption[Demo inicial con MediaPipe.]{Resultado de la demo inicial con MediaPipe en modo manos, mostrando \textit{landmarks} y conexiones sobre las manos detectadas.}
	\label{fig:AppDemoMediapipe1}
\end{figure}

Esta demo no se consideró un producto final. Su valor estuvo en reducir incertidumbre técnica y en ayudar al diseño de la aplicación final. A partir de ella se identificaron las partes que debían formalizarse: modelo de datos, permisos, factoría de modelos, \textit{pipelines}, almacenamiento temporal, trazabilidad y administración.

\section{Diseño de la aplicación escalable}

La segunda fase consistió en transformar la demo en una plataforma extensible. El objetivo fue evitar una aplicación cerrada, con modelos y flujos fijados directamente en el código. Para ello, el diseño se apoyó en tres ideas: arquitectura modular, modelo de datos extensible y ejecución desacoplada de modelos.

\subsection{Arquitectura modular}

La arquitectura se organizó siguiendo una adaptación práctica del patrón Modelo-Vista-Controlador, incorporando una capa adicional de servicios. Esta capa resulta especialmente importante porque evita que los controladores acumulen lógica de procesamiento de imágenes, selección de modelos o ejecución de \textit{pipelines}.

La Figura~\ref{fig:mvc-adaptado} representa esta organización general. La arquitectura no se limita al patrón clásico, sino que añade varios elementos propios del sistema:

\begin{itemize}
	\item \textbf{Factoría de aplicación Flask.} Centraliza la creación de la aplicación Flask, la configuración y el registro de módulos, funciona mediante \textbf{\textit{blueprints}} que separan rutas públicas, autenticación, tienda, \textit{pipelines} y administración.
	\item \textbf{Capa de servicios.} Contiene la lógica de negocio, ejecución de \textit{pipelines} y procesamiento de imágenes, en ella se encuentra una \textbf{factoría de inteligencia artificial.} Esta selecciona el motor de procesamiento adecuado sin acoplar los controladores a modelos concretos utilizando \textbf{\textit{Launchers}} que encapsulan la ejecución específica de cada familia de modelos.
\end{itemize}

\begin{figure}[htbp]
	\centering
	\includegraphics[width=0.78\textwidth]{mvc_adaptado.png}
	\caption[Arquitectura modular de la aplicación.]{Organización arquitectónica inspirada en Modelo-Vista-Controlador, con una capa adicional de servicios para separar la lógica de procesamiento.}
	\label{fig:mvc-adaptado}
\end{figure}

Esta separación permite que la lógica de entrada, la persistencia, la interfaz y la ejecución de modelos evolucionen de forma independiente.

\subsection{Modelo de datos como base de la escalabilidad}

El modelo de datos fue una de las partes clave del diseño, ya que permite escalar la aplicación sin depender de valores fijos en el código. La base de datos no solo representa usuarios, sino también roles, planes, suscripciones, alquileres de modelos, modelos de inteligencia artificial, modos de ejecución, \textit{pipelines}, etapas, ejecuciones y archivos temporales.

La Figura~\ref{fig:modelo-er} muestra el modelo entidad-relación del sistema. Su importancia está en que convierte los flujos de procesamiento en datos gestionables, no en funciones cerradas del código fuente.

\begin{figure}[htbp]
	\centering
	\includegraphics[width=0.92\textwidth]{DiagramaModeloER.png}
	\caption[Modelo entidad-relación del sistema.]{Modelo entidad-relación de la aplicación, utilizado como base para representar usuarios, permisos, modelos, modos, \textit{pipelines}, ejecuciones y archivos temporales.}
	\label{fig:modelo-er}
\end{figure}

La decisión más relevante fue separar los modelos de inteligencia artificial de sus modos de ejecución. De esta forma, un modelo puede disponer de varios modos, y cada etapa de un \textit{pipeline} debe indicar tanto el modelo como el modo utilizado. Esto permite validar que una etapa no combine un modo con un modelo al que no pertenece.

También se separó la ejecución lógica de los archivos físicos generados. La entidad de ejecución conserva la trazabilidad del análisis, mientras que los archivos temporales mantienen rutas internas, \textit{tokens} de descarga y fecha de expiración. Así, el historial puede conservarse aunque los archivos generados ya no estén disponibles.

\subsection{Pipelines de procesamiento}

Los \textit{pipelines} permiten pasar de una ejecución aislada de modelos a flujos formados por etapas. Cada etapa define qué modelo y qué modo deben ejecutarse, y en qué orden.

Esta estructura permite tres tipos de análisis:

\begin{itemize}
	\item \textbf{Análisis simples.} Una única etapa, como detección de objetos, manos o pose.
	\item \textbf{Análisis compuestos.} Varias etapas encadenadas sobre una misma imagen.
	\item \textbf{Análisis ramificados.} Una etapa genera varias imágenes intermedias y la siguiente se aplica sobre cada una de ellas.
\end{itemize}

El caso más representativo de ejecución ramificada es el recorte de personas. Una etapa puede localizar varios sujetos y generar un archivo por cada uno. Después, una etapa posterior puede aplicar estimación de pose o detección de manos sobre cada recorte. Esto obligó a tratar las salidas como colecciones de archivos, no como una única imagen final.

\subsection{Factoría de inteligencia artificial y launchers}

La factoría de inteligencia artificial evita que el ejecutor de \textit{pipelines} y los controladores dependan directamente de cada modelo concreto. Su objetivo es seleccionar el \textit{launcher} adecuado según el modelo y el modo solicitados, manteniendo el sistema preparado para poder escalarlo.

La Figura~\ref{fig:flujo-factory-pipeline} muestra el flujo de ejecución. El controlador valida la petición y delega en el ejecutor de \textit{pipelines}. Este recupera las etapas desde la base de datos y, para cada una, solicita a la factoría el \textit{launcher} correspondiente.

\begin{figure}[htbp]
	\centering
	\includegraphics[width=0.90\textwidth]{flujo_factory_pipeline.png}
	\caption[Flujo de ejecución de pipelines.]{Flujo de ejecución de \textit{pipelines} y resolución dinámica de modelos mediante la factoría de inteligencia artificial.}
	\label{fig:flujo-factory-pipeline}
\end{figure}

Esta decisión reduce el acoplamiento. Añadir una nueva familia de modelos no exige reescribir los controladores ni el ejecutor principal. El cambio se concentra en implementar un nuevo \textit{launcher}, registrarlo en la factoría y asociar sus modos en la base de datos.

\subsection{Configuración por etapas}

Cada modo dispone de una configuración predeterminada en formato JSON. Estos valores actúan como plantilla inicial para ejecutar una etapa, pero pueden modificarse antes de lanzar el análisis.

Esta separación permite distinguir entre:

\begin{itemize}
	\item \textbf{Configuración predeterminada.} Valores asociados al modo de ejecución.
	\item \textbf{Configuración aplicada.} Valores concretos utilizados en una ejecución.
\end{itemize}

Gracias a ello, el comportamiento de una etapa puede ajustarse sin modificar la función de procesamiento. Por ejemplo, puede cambiarse un umbral de confianza o un parámetro de detección manteniendo el mismo \textit{pipeline}.

\subsection{Permisos y lógica de acceso}

La aplicación incorpora autenticación mediante \textit{tokens} JWT y autorización mediante roles, planes y licencias temporales. Esta lógica permite controlar qué usuarios pueden acceder a cada funcionalidad y qué \textit{pipelines} tienen disponibles.

La plataforma diferencia entre:

\begin{itemize}
	\item \textbf{Administradores.} Acceden a funcionalidades de gestión y revisión global.
	\item \textbf{Usuarios con plan Pro.} Acceden a todos los \textit{pipelines} públicos y tienen una persistencia de archivos durante 30 días.
	\item \textbf{Usuarios básicos.} Acceden a \textit{pipelines} según los modelos contratados y vigentes, y sus archivos se almacenan 5 minutos.
\end{itemize}

Esta lógica convierte la aplicación en algo más completo que una demo de inferencia. Los modelos y \textit{pipelines} no solo existen en el sistema, sino que también están sujetos a reglas de acceso.

\section{Consolidación funcional}

La última fase consistió en completar la aplicación alrededor del diseño anterior. En esta fase se realizaron tareas de administración de \textit{pipelines}, gestión de resultados temporales, incorporación de pruebas automatizadas, análisis estático del código y preparación de un entorno reproducible.


\subsection{Administración de pipelines sin modificar código}

Una de las funcionalidades más importantes fue permitir la creación y edición de \textit{pipelines} desde la zona de administración. La Figura~\ref{fig:admin-pipelines} muestra esta parte de la interfaz, desde la que se pueden gestionar flujos formados por modelos y modos existentes.

\begin{figure}[htbp]
	\centering
	\includegraphics[width=0.70\textwidth]{admin_pipelines2.png}
	\caption[Administración de pipelines.]{Interfaz de administración para crear y editar \textit{pipelines} a partir de modelos y modos registrados.}
	\label{fig:admin-pipelines}
\end{figure}

Esta funcionalidad es relevante porque los \textit{pipelines} dejan de ser una lista fija escrita en el código. El administrador puede definir etapas, ordenarlas, habilitar o deshabilitar flujos y modificar su disponibilidad sin cambiar la lógica principal de procesamiento.

Antes de guardar un \textit{pipeline}, el \textit{backend} valida que:

\begin{itemize}
	\item El modelo exista y esté habilitado.
	\item El modo exista y esté habilitado.
	\item El modo pertenezca realmente al modelo indicado.
	\item Las etapas tengan una estructura válida.
	\item El \textit{pipeline} pueda guardarse sin romper restricciones de base de datos.
\end{itemize}

Esta doble validación, desde aplicación y desde base de datos, refuerza la coherencia del sistema.

\subsection{Resultados temporales y ciclo de vida de los datos}

El procesamiento de imágenes genera archivos que no deben exponerse mediante rutas internas del servidor. Para resolverlo, cada archivo generado se asocia a una ejecución y a un \textit{token} de descarga.

Este diseño aporta varias ventajas:

\begin{itemize}
	\item Oculta las rutas reales del servidor.
	\item Relaciona cada archivo con una ejecución concreta.
	\item Permite controlar la expiración de resultados.
	\item Mantiene trazabilidad aunque el archivo temporal desaparezca.
\end{itemize}

Además, se incorporaron tareas de mantenimiento para eliminar archivos expirados, renovar servicios cuando corresponde y anonimizar cuentas dadas de baja tras el periodo definido.

\subsection{Reproducibilidad: datos iniciales y Docker}

Para que la aplicación pueda probarse sin configurar manualmente todos los datos, se incorporó un \textit{script} de inicialización. Este \textit{script} prepara un entorno de demostración con usuarios, roles, planes, modelos de inteligencia artificial, modos y \textit{pipelines} ya configurados.

Junto a los datos iniciales, se preparó un despliegue reproducible mediante Docker Compose. La aplicación se organiza en un contenedor para Flask y otro para MariaDB. De este modo, el entorno de ejecución queda definido de forma más controlada y se reducen errores derivados de diferencias entre equipos, versiones de dependencias o configuración del sistema operativo.

\begin{itemize}

\end{itemize}

\subsection{Actualización visual de la aplicación}

En la fase final del proyecto se realizó una actualización de los estilos de la aplicación. Esta mejora no modificó la lógica interna del sistema ni las funcionalidades implementadas, sino que se centró únicamente en renovar la apariencia visual de las interfaces.

El cambio consistió en unificar la estética general de las distintas vistas, aplicando una línea visual más moderna. Para ello se revisaron colores, fondos, tarjetas, botones, formularios, tablas y distribución visual de los elementos.

Como apoyo en esta tarea se utilizó inteligencia artificial generativa, principalmente para proponer alternativas de diseño, reorganizar reglas CSS y acelerar la adaptación visual de las pantallas. Las propuestas generadas fueron revisadas e integradas manualmente en el proyecto, manteniendo el control sobre los cambios aplicados.

Además, se incorporó la posibilidad de alternar entre modo claro y modo oscuro, utilizando variables de estilo para mantener una apariencia consistente en ambos temas. De este modo, la aplicación conserva su funcionamiento original, pero presenta una interfaz visualmente más moderna.
