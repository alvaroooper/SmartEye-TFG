\capitulo{5}{Aspectos relevantes del desarrollo del proyecto}

Este capítulo recoge las decisiones más relevantes adoptadas durante el desarrollo del TFG, tanto desde el punto de vista técnico como desde la lógica que ha guiado la evolución del proyecto. No se pretende describir únicamente las tecnologías empleadas, sino justificar las principales elecciones realizadas en las fases de análisis, diseño e implementación.

El desarrollo ha pasado por dos etapas principales. En primer lugar, se construyó una demo funcional para validar la viabilidad técnica del procesamiento de imágenes mediante modelos de inteligencia artificial. Posteriormente, el trabajo evolucionó hacia la aplicación real, abordando la definición de requisitos, la delimitación del producto mínimo viable, el diseño del modelo de datos, la migración del entorno de desarrollo a Debian y la implementación inicial de la base de datos en MariaDB.

\section{Enfoque general y ciclo de vida}

El proyecto se ha desarrollado siguiendo un enfoque \textbf{iterativo e incremental}. En lugar de comenzar directamente con una aplicación completa, se optó por construir primero una demo que permitiera comprobar la viabilidad del procesamiento de imágenes, validar el flujo básico de trabajo y detectar problemas tempranos relacionados con dependencias, rutas, formatos y gestión de ficheros.

Esta estrategia permitió reducir incertidumbre en las primeras fases y tomar decisiones posteriores con una base práctica. Una vez validado el flujo principal, el proyecto pasó a una etapa más formal de análisis y diseño orientada a la construcción de una aplicación real.

\section{Planteamiento inicial del problema}

El objetivo del TFG es desarrollar una aplicación web capaz de actuar como servidor para ejecutar modelos de inteligencia artificial sobre imágenes, devolviendo tanto resultados estructurados como una imagen procesada.

Desde el inicio se definieron varios principios que han guiado el desarrollo:

\begin{itemize}
	\item \textbf{Resultado visual como salida principal}, complementado con información estructurada en JSON.
	\item \textbf{Extensibilidad}, de forma que puedan añadirse nuevos modelos y modos sin rediseñar el núcleo del sistema.
	\item \textbf{Separación de responsabilidades}, diferenciando la API de la interfaz web.
	\item \textbf{Evolución hacia pipelines}, permitiendo en el futuro encadenar varias etapas de procesamiento.
\end{itemize}

Por tanto, el problema no consistía sólo en ejecutar un modelo sobre una imagen, sino en sentar las bases de una aplicación ampliable, mantenible y preparada para incorporar control de acceso, catálogo de IAs, persistencia y trazabilidad de ejecuciones.

\section{Elección tecnológica: Flask y ecosistema Python}

Para el backend se eligió \textbf{Python} junto con \textbf{Flask}. Python resultaba una elección natural por su amplio uso en inteligencia artificial y visión por computador, así como por la disponibilidad de bibliotecas maduras para tratamiento de imágenes y ejecución de modelos.

Flask se seleccionó por su ligereza y flexibilidad. En una fase inicial de experimentación resultaba importante trabajar con una herramienta que permitiera construir una API funcional con rapidez, sin imponer una estructura excesivamente rígida. Al mismo tiempo, Flask permite evolucionar posteriormente hacia una organización más modular basada en rutas, servicios y separación de capas.

Además, el ecosistema de Python facilitó integrar bibliotecas clave como \textbf{OpenCV} y \textbf{NumPy}, utilizadas para la carga, representación, manipulación y almacenamiento de imágenes.

\section{Selección de modelos para la demo}

Para la demo inicial se eligieron dos familias de modelos complementarias: \textbf{YOLO} y \textbf{MediaPipe}. La finalidad de esta elección fue validar distintos tipos de procesamiento y obtener salidas visuales claras que permitiesen comprobar de forma inmediata el funcionamiento del sistema.

YOLO se utilizó como modelo de detección general de objetos. Su salida, basada en cajas delimitadoras, etiquetas y niveles de confianza, resulta muy adecuada para una validación rápida del procesamiento.

MediaPipe se incorporó para trabajar con landmarks, concretamente en los modos \texttt{hands} y \texttt{pose}. Esto permitió demostrar que el sistema no sólo podía manejar detecciones por caja, sino también estructuras más ricas basadas en puntos clave y conexiones anatómicas.

La combinación de ambos modelos permitió validar dos tipos de análisis frecuentes en visión por computador: detección de objetos y detección de landmarks.

\section{Construcción de la demo}

La demo se desarrolló con dos objetivos principales: comprender el flujo técnico completo del procesamiento de imágenes y validar una primera organización interna del sistema.

En esta fase se consiguió implementar un flujo completo de extremo a extremo:

\begin{itemize}
	\item Subida de una imagen desde el cliente;
	\item Ejecución del modelo y modo seleccionados;
	\item Devolución de una salida estructurada;
	\item Generación de una imagen anotada.
\end{itemize}

Este resultado permitió comprobar la viabilidad del procesamiento, la correcta comunicación cliente-servidor y la integración de distintos modelos bajo una misma lógica de uso.

\section{Decisiones de diseño relevantes en la demo}

Una de las decisiones más importantes fue organizar la lógica de IA mediante tareas especializadas y una factoría central. Esta estructura permitió separar la selección del modelo y del modo de la capa HTTP, evitando condicionales dispersos y facilitando la extensibilidad del sistema.

También se consideró fundamental separar la \textbf{API REST} de la \textbf{interfaz web}. La API quedó orientada a integración y pruebas, mientras que la interfaz web se mantuvo como punto de acceso visual para demostración y uso interactivo. Esta separación simplificó la organización del proyecto y resulta coherente con la evolución posterior de la aplicación.

Otro aprendizaje importante estuvo relacionado con la gestión de rutas y la entrega de ficheros generados. Fue necesario resolver correctamente la ubicación de los resultados, su almacenamiento y su acceso posterior desde el navegador. Aunque se trata de un aspecto técnico concreto, resultó decisivo para convertir la prueba inicial en una demo realmente utilizable.

Por último, la interfaz se adaptó para reflejar dinámicamente los modelos y modos disponibles. Esta decisión mejoró la experiencia de uso y redujo el acoplamiento entre frontend y backend.

\section{Aspectos relevantes de implementación}

Durante la demo se consolidó un flujo interno común para el tratamiento de imágenes: recepción de la imagen, decodificación a una matriz de \texttt{NumPy}, procesamiento con el modelo correspondiente, anotación sobre la imagen y almacenamiento del resultado.

También se estableció una salida dual compuesta por un JSON estructurado y una imagen procesada. Esta combinación aporta, por un lado, trazabilidad e integración y, por otro, una evidencia visual inmediata del funcionamiento del sistema.

\section{Limitaciones de la demo y necesidad de evolución}

La demo cumplió su función principal: validar la viabilidad técnica del procesamiento y establecer una primera arquitectura extensible. Sin embargo, seguía siendo un prototipo con limitaciones claras: ausencia de persistencia completa, falta de gestión de usuarios y permisos, trazabilidad reducida, ejecución aislada de tareas y una robustez todavía insuficiente para una aplicación real.

Por ello, la demo no debía entenderse como una versión final reducida, sino como una fase de validación y aprendizaje previa a la construcción formal del sistema.

\section{De la demo a la aplicación real}

Una vez validada la viabilidad técnica, el proyecto pasó a una nueva etapa centrada en la aplicación real. A partir de este punto, el objetivo dejó de ser únicamente demostrar que el procesamiento funcionaba y pasó a ser construir un sistema coherente, mantenible y preparado para crecer.

El primer paso consistió en definir los requisitos funcionales, no funcionales y los casos de uso del sistema completo. Esto permitió trabajar desde una visión global y no desde funcionalidades aisladas. A partir de esa visión general se delimitó después el \textbf{producto mínimo viable (MVP)}, entendido como un subconjunto coherente del sistema final y no como una simple reducción arbitraria.

Este enfoque permitió centrar la primera iteración en el flujo principal de valor de la aplicación sin comprometer la coherencia del diseño a medio plazo.

\section{Diseño de datos y persistencia}

Una vez definidos los casos de uso, el trabajo avanzó hacia el diseño de la persistencia. Se elaboraron el diagrama Entidad-Relación y el modelo relacional con el objetivo de traducir el comportamiento esperado del sistema a una estructura de datos robusta.

Durante este modelado se siguieron varios criterios: separación clara de conceptos, reducción de redundancia, preparación para el crecimiento, trazabilidad e integridad de negocio. Gracias a ello, el sistema pudo representarse mediante entidades como usuarios, roles, planes, suscripciones, modelos IA, modos, pipelines y ejecuciones.

La principal utilidad de este diseño fue doble: por un lado, servir como documentación; por otro, facilitar una implementación posterior en MariaDB más coherente y menos improvisada.

\section{Migración del entorno de desarrollo a Debian}

Otra decisión relevante fue la migración del entorno de desarrollo a \textbf{Debian}. Esta elección respondió a motivos técnicos: mayor cercanía al entorno de despliegue habitual de aplicaciones web, mejor integración con herramientas de backend, tratamiento más consistente de rutas y permisos, y mayor facilidad para la automatización y la administración del sistema.

En el contexto de este TFG, Debian aportó un entorno más natural para trabajar con Python, Flask y MariaDB, además de acercar el desarrollo a un escenario más realista de despliegue.

\section{Implementación de la base de datos en MariaDB}

Con el modelo relacional ya definido y el entorno estabilizado en Debian, se procedió a la implementación inicial de la base de datos en \textbf{MariaDB}. Esta fase permitió trasladar al plano físico las decisiones adoptadas en el diseño, mediante claves primarias, restricciones \texttt{UNIQUE}, claves foráneas, valores por defecto e integridad transaccional.

La importancia de esta etapa radica en que el proyecto dejó de depender únicamente de la lógica de procesamiento de la demo y pasó a disponer de una base persistente para gestionar usuarios, permisos, configuraciones y ejecuciones de forma coherente.
