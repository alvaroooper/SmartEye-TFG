\section{Diseño de datos}

El modelo de datos se ha diseñado para representar de forma separada las entidades principales del sistema: usuarios, roles, planes, modelos de IA, pipelines, ejecuciones y archivos temporales. Esta división reduce redundancias, mantiene la trazabilidad de las operaciones y facilita futuras ampliaciones de la aplicación.

\subsection{Relaciones principales y valoración del modelo}

\begingroup
\small
Las relaciones más relevantes del modelo son:

\begin{itemize}
	\setlength{\itemsep}{0.25em}
	\setlength{\parsep}{0pt}
	\item \textbf{\texttt{USUARIO} -- \texttt{ROL}}: relación muchos a muchos mediante \texttt{USUARIO\_ROL}.
	\item \textbf{\texttt{USUARIO} -- \texttt{SUSCRIPCION\_PLAN} -- \texttt{TIPO\_PLAN}}: registra la contratación de planes.
	\item \textbf{\texttt{USUARIO} -- \texttt{ALQUILA} -- \texttt{IA\_MODELO}}: registra el acceso individual a modelos.
	\item \textbf{\texttt{IA\_MODELO} -- \texttt{IA\_MODO}}: permite que un modelo tenga varios modos de ejecución.
	\item \textbf{\texttt{PIPELINE} -- \texttt{PIPELINE\_ETAPA}}: define flujos compuestos por etapas ordenadas.
	\item \textbf{\texttt{IA\_MODO} -- \texttt{PIPELINE\_ETAPA}}: conecta cada etapa con el modo de IA que debe ejecutar.
	\item \textbf{\texttt{USUARIO} -- \texttt{EJECUCION} -- \texttt{PIPELINE}}: registra qué usuario ejecuta qué pipeline.
	\item \textbf{\texttt{EJECUCION} -- \texttt{TEMPORAL\_ARCHIVO}}: asocia los archivos temporales a la ejecución que los genera.
\end{itemize}

El modelo cubre las funcionalidades principales de la aplicación: autenticación, roles, planes, alquileres de modelos, definición de pipelines, ejecución de análisis y gestión de archivos temporales. La separación entre catálogo y operaciones concretas permite conservar histórico aunque cambien precios, planes o modelos.

Además, la separación entre \texttt{PIPELINE} y \texttt{PIPELINE\_ETAPA} permite definir flujos configurables sin codificarlos de forma fija. Para mantener la integridad, se usa \texttt{RESTRICT} en información histórica, \texttt{CASCADE} en dependencias fuertes y \texttt{SET NULL} cuando interesa conservar un registro aunque desaparezca su propietario.
\endgroup

\section{Diseño arquitectónico}

El diseño arquitectónico describe cómo se organiza internamente la aplicación y cómo se reparten las responsabilidades entre interfaz, controladores, servicios, modelos y base de datos.

La aplicación se ha desarrollado con \texttt{Flask}. Por ello, no se aplica un patrón MVC clásico de forma estricta, sino una adaptación en la que los \texttt{Blueprints} actúan como controladores, las plantillas HTML y respuestas JSON como vistas, y las clases SQLAlchemy como modelo persistente. Además, se incorpora una capa de servicios para aislar la lógica de negocio y el procesamiento de imágenes.

De forma resumida, la arquitectura se organiza en los siguientes bloques:

\begin{itemize}
	\item \textbf{Cliente}: navegador desde el que el usuario interactúa con la aplicación.
	\item \textbf{Vistas}: plantillas HTML y respuestas JSON generadas por la aplicación.
	\item \textbf{Controladores}: módulos Flask encargados de recibir peticiones, validar datos, comprobar permisos y devolver respuestas.
	\item \textbf{Servicios}: lógica interna de ejecución de pipelines, selección de modelos y procesamiento de imágenes.
	\item \textbf{Modelo}: entidades SQLAlchemy que representan usuarios, roles, planes, modelos, pipelines, ejecuciones y archivos temporales.
	\item \textbf{Base de datos}: persistencia principal del sistema.
\end{itemize}

A continuación se presentan tres vistas complementarias: la arquitectura general, la organización real de módulos y la estructura de la capa de servicios.

\subsection{Arquitectura MVC adaptada a Flask con capa de servicios}

La Figura~\ref{fig:arquitectura_mvc_flask_servicios} muestra la arquitectura general de la aplicación. En ella se observa cómo el cliente se comunica con Flask mediante peticiones HTTP, que son atendidas por controladores y derivadas, cuando es necesario, hacia servicios internos o hacia la capa de persistencia.

\begin{figure}[H]
	\centering
	\includegraphics[width=\textwidth]{img/mvc_adaptado.png}
	\caption[Arquitectura MVC adaptada a Flask]{Arquitectura MVC adaptada a Flask con capa de servicios.}
	\label{fig:arquitectura_mvc_flask_servicios}
\end{figure}

Los controladores son \texttt{auth\_controller.py}, \texttt{shop\_controller.py} y \texttt{pipeline\_controller.py}. El primero gestiona autenticación, registro, perfil y usuarios; el segundo agrupa las operaciones de tienda, planes y alquileres; y el tercero concentra la consulta, configuración, ejecución e historial de pipelines.

La capa de servicios evita que los controladores acumulen toda la lógica. En especial, permite separar la ejecución de pipelines y la resolución de modelos de IA respecto de las rutas HTTP. Esta decisión mejora la mantenibilidad y facilita añadir nuevos modelos, modos o flujos de procesamiento.

El modelo persistente se implementa mediante SQLAlchemy, manteniendo una correspondencia directa con las tablas descritas en el diseño de datos. Esta separación también favorece las pruebas, ya que permite probar controladores, servicios y persistencia de forma más aislada.

\subsection{Organización de módulos y dependencias principales}

La Figura~\ref{fig:modulos_dependencias} muestra la organización real del proyecto a nivel de archivos, paquetes y dependencias principales.

\begin{figure}[H]
	\centering
	\includegraphics[width=\textwidth]{img/diagrama_modulos_dependencias_organizado.png}
	\caption[Vista de módulos y dependencias]{Vista de módulos y dependencias principales de la aplicación.}
	\label{fig:modulos_dependencias}
\end{figure}

El punto de entrada se encuentra en \texttt{run.py}, que crea la aplicación mediante \texttt{create\_app()}. La configuración se centraliza en \texttt{config.py}, mientras que \texttt{app/\_\_init\_\_.py} inicializa extensiones como SQLAlchemy y JWT, carga la configuración y registra los \texttt{Blueprints}.

La carpeta \texttt{app/controllers} contiene las rutas HTTP y las validaciones iniciales. La carpeta \texttt{app/templates} agrupa las plantillas HTML de la interfaz. La lógica de aplicación se sitúa en \texttt{app/services}, donde se encuentran el orquestador de pipelines y la factoría de modelos de IA. Por su parte, \texttt{app/models.py} concentra las entidades SQLAlchemy.

También existen recursos auxiliares, como las configuraciones de ejecución en \texttt{configs}, los modelos locales en carpetas de \texttt{models} y los archivos temporales generados durante las ejecuciones. Finalmente, el paquete \texttt{tests} contiene las pruebas automatizadas, ejecutadas en un entorno aislado.

Esta organización refleja la arquitectura definida: entrada, configuración, controladores, servicios, modelo, recursos y pruebas quedan separados en componentes diferenciados.

\subsection{Diagrama de clases y módulos principales de la capa de servicios}

La Figura~\ref{fig:clases_modulos_capa_servicios} muestra los elementos principales que intervienen en la ejecución de pipelines y en la resolución dinámica de modelos de inteligencia artificial.

\begin{figure}
	\centering
	\includegraphics[width=\textwidth]{img/diagrama_clases_tfg.png}
	\caption[Diagrama de la capa de servicios]{Diagrama de clases y módulos principales de la capa de servicios.}
	\label{fig:clases_modulos_capa_servicios}
\end{figure}

El flujo parte de \texttt{pipeline\_controller}, que recibe la solicitud de ejecución, valida la imagen, comprueba permisos y delega el procesamiento en \texttt{PipelineRunner}. Este servicio recorre las etapas del pipeline, obtiene la configuración aplicable y solicita a la factoría el lanzador correspondiente.

La factoría de IA desacopla el orquestador de las implementaciones concretas. Si una etapa requiere YOLO, se selecciona el lanzador correspondiente; si requiere MediaPipe, se utiliza el lanzador asociado a ese modelo. Cada lanzador encapsula la lógica específica y delega finalmente en los módulos funcionales de procesamiento.

Gracias a esta estructura, los pipelines no quedan codificados como funciones fijas, sino como secuencias de etapas almacenadas y configurables. Esto permite que el administrador modifique la composición de los pipelines desde la aplicación y facilita la incorporación futura de nuevos modelos o modos de ejecución.

\section{Diseño de interfaces}

El diseño de interfaces recoge la organización visual y de navegación de la aplicación web. La interfaz se ha construido mediante plantillas HTML renderizadas desde Flask y lógica JavaScript para consumir los endpoints del backend.

Desde el punto de vista funcional, las pantallas se agrupan en tres zonas: zona pública, zona de usuario autenticado y zona de administración. Esta separación permite diferenciar claramente las acciones disponibles para cada tipo de usuario.

\subsection{Criterios de diseño}

El diseño de la interfaz se ha realizado siguiendo los siguientes criterios:

\begin{itemize}
	\setlength{\itemsep}{0.25em}
	\item \textbf{Claridad}: cada pantalla muestra únicamente la información necesaria para su función.
	\item \textbf{Separación por perfiles}: las operaciones de usuario y administración aparecen en zonas distintas.
	\item \textbf{Coherencia de navegación}: las páginas principales mantienen enlaces hacia las secciones relacionadas.
	\item \textbf{Retroalimentación}: los formularios muestran mensajes de error o confirmación.
	\item \textbf{Ocultación de complejidad}: el usuario no necesita conocer la estructura interna de modelos, controladores o archivos temporales.
\end{itemize}

\subsubsection*{\textit{Prompt} utilizado para la mejora visual}

Una vez validada la funcionalidad principal de la aplicación, se utilizó inteligencia artificial generativa como apoyo para actualizar los estilos visuales. El \textit{prompt} utilizado fue el siguiente:
\newtcolorbox{promptbox}{
	breakable,
	colback=gray!5,
	colframe=gray!60,
	boxrule=0.4pt,
	arc=2mm,
	left=2mm,
	right=2mm,
	top=1.5mm,
	bottom=1.5mm,
	fontupper=\scriptsize\ttfamily,
	before upper={
		\setlength{\parindent}{0pt}
		\setlength{\parskip}{0.65em}
	}
}
\begin{promptbox}
	Actúa como un desarrollador frontend senior especializado en aplicaciones web Flask. Analiza el proyecto completo que se proporciona en el archivo \texttt{proyecto\_completo.txt} y mejora únicamente la parte visual de las interfaces, sin modificar la lógica del backend ni los endpoints existentes.
	
	El objetivo es rediseñar las plantillas HTML para conseguir una interfaz moderna, profesional, responsive y coherente en todas las páginas de la aplicación: inicio, login, registro, panel de usuario, tienda, guía de compra, compras, historial, perfil, resultados y administración.
	
	La mejora debe unificar la gama de colores, tipografía, botones, formularios, tarjetas, tablas, menús y mensajes de estado. Para evitar repetición de código, crea estilos comunes reutilizables en ficheros CSS dentro de \texttt{app/static/css} y utiliza plantillas base, bloques Jinja o componentes reutilizables en \texttt{app/templates} cuando sea conveniente.
	
	No extraigas el JavaScript existente a ficheros \texttt{.js} externos. Si es necesario ajustar algo de JavaScript para adaptar la interfaz, mantenlo dentro de las propias plantillas HTML y conserva los identificadores, funciones y eventos que ya usa la aplicación.
	
	No cambies rutas, endpoints, identificadores usados por JavaScript, llamadas \texttt{fetch}, gestión de JWT ni comportamiento funcional. Solo puedes reorganizar HTML y CSS si la funcionalidad se mantiene intacta.
	
	El resultado debe incluir los archivos creados o modificados y el código completo necesario para aplicar el rediseño, asegurando que la aplicación sigue siendo mantenible, escalable y usable en dispositivos móviles, tabletas y escritorio.
	
	Además, la interfaz debe permitir alternar entre modo claro y modo oscuro. Ambos temas deben compartir la misma estructura visual y estar definidos mediante variables CSS reutilizables. El cambio de tema debe mantener la preferencia del usuario durante la navegación.
\end{promptbox}
